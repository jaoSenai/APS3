# ADR 0001 — Validação assíncrona de laudos via RabbitMQ com upload direto para Object Storage

Status: Aprovado

## Contexto

Quando a vendedora publica um resíduo Classe I, ela precisa anexar laudo e FDS. Esses PDFs podem ser bem pesados (às vezes passam de 20 MB), e validar cada um (formato, tamanho, assinatura, antivírus) demora alguns segundos. Se tudo isso acontecesse dentro da mesma requisição HTTP de publicar a oferta, a API ficaria travada esperando, a vendedora ficaria olhando pra tela carregando e, com várias indústrias publicando ao mesmo tempo, o servidor ia sofrer. Além disso, a restrição R04 pede busca de catálogo abaixo de 1,5 s, então a API não pode ficar ocupada com arquivo pesado.

Outro ponto é a consistência: uma oferta Classe I não pode aparecer no catálogo sem laudo validado, de jeito nenhum.

 Decisão

Decidimos separar o fluxo em duas partes:

1. **Upload direto:** a API só gera uma URL pré-assinada do MinIO (compatível com S3), e o navegador manda o arquivo direto pra lá. O arquivo nem passa pela API.
2. **Validação assíncrona:** quando o laudo é anexado, a Oferta publica um `LaudoAnexadoEvent` no RabbitMQ. Um worker separado consome a fila, valida o documento e só então chama `enviarParaModeracao()`.

Escolhemos RabbitMQ em vez de Kafka porque o volume é moderado, a gente precisa de confirmação por mensagem (ack) e de fila de mensagens mortas (dead-letter) pra reprocessar, e ele é bem mais simples de operar pra um time pequeno. A máquina de estados da Oferta garante que, enquanto o worker não confirmar, a oferta fica presa em `AguardandoLaudo` ou `ValidandoLaudo`.

 Consequências

Vantagens:
- A API responde rápido (201 Created) e não fica travada.
- O worker escala separado da API se a fila crescer.
- Se a validação falhar, a mensagem volta pra fila ou vai pra dead-letter, e nada se perde.
- O estado da oferta fica protegido: Classe I sem laudo válido nunca chega em `Ativa`.

Débitos e riscos aceitos:
- A consistência passa a ser eventual: a vendedora não vê o resultado na hora e depende de notificação.
- Mais infraestrutura pra manter (RabbitMQ e MinIO).
- O worker precisa ser idempotente, porque a mesma mensagem pode chegar duas vezes.
- Fica mais difícil de depurar, então vamos precisar de logs com ID de correlação desde a Sprint 3.
